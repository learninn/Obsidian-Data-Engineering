**SCD (Slowly Changing Dimension)** — подход к обновлению и поддержке данных, хранящихся в таблицах измерений, по мере их изменения.

| Тип (Type) | Название / Суть      | Что происходит с историей                                                                                                                                  | Когда использовать                                                                                                                        |
| ---------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Type 0** | **Fixed / Original** | **Не меняется.** Значение фиксируется навсегда, обновления игнорируются.                                                                                   | Данные, которые не должны меняться: дата рождения, оригинальный ID, код страны регистрации.                                               |
| **Type 1** | **Overwrite**        | **История не сохраняется.** Новое значение просто перезаписывает старое.                                                                                   | Исправление ошибок, обновление контактных данных. Важно: все старые факты начнут ссылаться на новое значение.                             |
| **Type 2** | **Row Versioning**   | **Полная история.** На каждое изменение создается новая строка с новым Surrogate Key, датами начала/конца (`valid_from` / `valid_to`) и флагом is_current. | **Самый популярный.** Нужен, когда важно знать состояние атрибута на момент совершения транзакции (например, где жил клиент при покупке). |
| **Type 3** | **Previous Value**   | **Ограниченная история.** Добавляется колонка «предыдущее значение» рядом с текущим.                                                                       | Когда нужно сравнить «сейчас» только с «одним шагом назад». Используется редко.                                                           |
| **Type 4** | **History Table**    | **Разделение.** Текущие данные в основной таблице, вся история — в отдельной таблице.                                                                      | Когда основная таблица должна быть легкой и быстрой, а история нужна редко.                                                               |
| **Type 6** | **Hybrid (1+2+3)**   | **Гибрид.** Сохраняет полную историю (как Type 2), но в каждой строке также хранит текущее и предыдущее значения.                                          | Нужна максимальная гибкость: и исторические срезы, и быстрый доступ к текущему статусу.                                                   |

# Краткий дайджест: советы по каждому типу SCD

|Тип|Главный совет|Подводные камни|Ключевой нюанс реализации|
|---|---|---|---|
|**Type 0**|Не трогай. Зафиксировал — и забыл.|Если ошиблись при загрузке — исправить можно только через Type 1 или перезаливку.|Обычно это атрибуты, которые физически не могут измениться (дата рождения, исходный ID).|
|**Type 1**|Используй для **исправления ошибок**, а не для отслеживания изменений.|Все исторические факты «поедут» — старые транзакции начнут ссылаться на новое значение.|Не требует новых ключей. Делай `UPDATE`, а не `INSERT`. Осторожно с ETL: нельзя просто перезаписать, если downstream уже посчитал агрегаты.|
|**Type 2**|Стандарт де-факто. Если сомневаешься — бери Type 2.|Раздувание таблицы + сложные джойны (нужно фильтровать по дате или флагу `is_current`).|Обязательно: Surrogate Key, `valid_from`, `valid_to`, `is_current`. Для «закрытия» старой строки ставь `valid_to = дата_изменения - 1 день` (или `9999-12-31` для открытой).|
|**Type 3**|Бери только если бизнес явно просит «сравнить с прошлым».|Хранит лишь 1 шаг назад. При третьем изменении первое значение теряется навсегда.|Добавляй колонки `current_value` и `previous_value`. Не масштабируется — при N изменениях нужны N колонок.|
|**Type 4**|Используй, когда основная таблица должна оставаться быстрой.|Два источника правды — легко забыть синхронизировать историю и текущее.|Основная таблица = только актуальное. History-таблица = append-only. Джойн только когда реально нужна история.|
|**Type 6**|Гибрид «всё в одном» — но не усложняй без необходимости.|Самая сложная логика загрузки. Легко получить рассинхрон между историческими и текущими колонками.|Комбинация: новая строка (Type 2) + колонка `current_value` (Type 1) + `previous_value` (Type 3). Идеален для BI, где нужны и срезы, и «актуальный статус» в одной строке.|
