**SCD1 (Slowly Changing Dimension Type 1)** — это метод обновления измерений в хранилище данных, при котором старые значения атрибутов **просто перезаписываются** новыми. История изменений не сохраняется, в таблице всегда отражается только текущее состояние записи.

**Основной принцип:** Стратегия Upsert. Если запись уже существует (определяется по бизнес-ключу), ее поля обновляются (`UPDATE`). Если записи нет — она вставляется как новая (`INSERT`).

**Ключевая особенность:** Естественный и суррогатный ключ (ID записи) остается прежним. Все факты в связанных таблицах автоматически начинают ссылаться на обновленные данные «задним числом».

**Когда использовать:**

- **Исправление ошибок:** Если в исходных данных была опечатка (неверный телефон клиента).
    
- **Нетребовательность к истории:** Атрибут не нужен для исторического анализа (например, текущий email или номер телефона клиента).

## Реализация

Реализация SCD1 сводится к операции слияния (Merge) или Upsert (`UPDATE` + `INSERT`).
Основная задача — сравнить входящий поток данных (Staging) с текущей таблицей измерения (Dimension) по бизнес-ключу и выполнить соответствующие действия.

### Сценарий А: Запись найдена (Match)

- Сравниваются значения атрибутов.
    
- Если значения **отличаются**, выполняется `UPDATE` целевой строки. Обновляются только те поля, которые изменились (или все поля, в зависимости от реализации).
    
- Если значения **совпадают**, ничего не делается (пропуск, чтобы избежать лишних операций записи).


### Сценарий Б: Запись не найдена (No Match)

- Выполняется `INSERT` новой строки. Если используется суррогатный ключ, он генерируется (например, через последовательность/sequence).


### Сценарий В: Запись есть в цели, но нет в источнике (Delete)

- В классическом SCD1 это **не обрабатывается** автоматически. Если запись исчезла из источника, она обычно остается в измерении (так как это измерение, а не факт). Удаление (hard delete) или логическое удаление (soft delete) применяется только по отдельному бизнес-требованию.


**Hard delete (жёсткое удаление)**

Строка **физически удаляется** из таблицы. После `DELETE` (и `COMMIT`) данных больше нет — восстановить можно только из бэкапа или из архива/WAL-логов.

**Плюсы:**

- Таблица не растёт «мусором», нет лишних строк.
    
- Простые запросы — не нужно фильтровать `WHERE is_deleted = false`.
    
- Экономия места.

**Минусы:**

- **Необратимость** — случайное удаление = потеря данных.
    
- **Ломает ссылочную целостность**: если на строку ссылаются факты (FK), `DELETE` либо упадёт, либо потребует `ON DELETE CASCADE` (что удалит и факты — обычно **катастрофа** для DWH).
    
- **Теряется история**: нельзя ответить на вопрос «а был ли этот клиент/товар раньше?».
    
- В DWH/измерениях применяется **редко** — обычно только для **очистки ошибочно загруженных данных** или по **требованиям GDPR** (право на забвение).


**Soft delete (мягкое удаление)**

Строка **остаётся в таблице**, но помечается как удалённая — через **флаг** или **timestamp**. Все запросы должны явно исключать такие строки.
Использование **timestamp лучше**, т.к. хранит и факт, и время удаления.


* **Флаг:**
```sql
UPDATE dim_table SET is_deleted = true WHERE business_key = 123;
```

* **timestamp:**
```sql
UPDATE dim_table SET deleted_at = now() WHERE business_key = 123;
```

* **Чтение «живых» строк:**
```sql
UPDATE dim_table SET deleted_at = now() WHERE business_key = 123;
```


**Плюсы:**

- **Обратимость** — можно «восстановить» (`UPDATE ... SET deleted_at = NULL`).
    
- **Сохраняется история** и ссылочная целостность — факты продолжают ссылаться на строку.
    
- Аудит: видно, что и когда удалили.
    
- В SCD-контексте — удобно для отслеживания «исчезнувших» из источника записей.
    

**Минусы:**

- **Риск забыть фильтр** — самый частый баг: запрос без `WHERE deleted_at IS NULL` вернёт «удалённые» строки.
- Решения: представления (VIEW), Row-Level Security (RLS) в PostgreSQL, или переименование таблицы + VIEW с фильтром.
    
- Таблица растёт, нужна периодическая архивация/партиционирование.
