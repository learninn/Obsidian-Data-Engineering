**SCD6 (Slowly Changing Dimension Type 6)** — это гибридный метод обновления измерений в хранилище данных, при котором для каждого отслеживаемого атрибута создаются две колонки — **историческая** и **текущая**, что одновременно обеспечивает полную хронологию изменений, быстрый доступ к актуальному значению без соединений и доступ к предыдущему значению атрибута.


**Когда использовать:**

- Отчёты, чувствительные к историческому состоянию атрибута на момент факта (как в SCD2)
    
- Отчёты, группирующие факты по актуальному значению атрибута **без соединения** с дополнительными таблицами (как в SCD1)
    
- Нужен доступ к непосредственно предыдущему значению атрибута (как в SCD3)
    
- Требуется единая таблица измерения вместо разделения на current/history (в отличие от SCD4)


### Целевая таблица содержит:

|Компонент|Назначение|
|---|---|
|Surrogate Key|Уникальный идентификатор версии (генерируется в DWH)|
|Natural Key|Бизнес-ключ источника|
|`attribute_historical`|Значение атрибута, действовавшее в период данной версии строки|
|`attribute_current`|Актуальное значение атрибута — **одинаковое для всех строк** данной сущности|
|`valid_from`|Начало действия версии|
|`valid_to`|Окончание действия (NULL / high-date для текущей)|
|`is_current`|Флаг актуальной версии (денормализация для производительности)|


**Инварианты:**

- Для каждого natural key интервалы `[valid_from, valid_to)` не пересекаются и покрывают всю временную ось (как в SCD2).
    
- Для каждого natural key существует **ровно одна** строка с `is_current = TRUE`.
    
- Колонки `attribute_current` для всех строк одной сущности содержат **одинаковое** значение — последнее актуальное.


### ETL-логика

Обработка входящего потока выполняется в следующей последовательности. Все операции, изменяющие целевую таблицу, выполняются в одной транзакции.

**1. Обнаружение изменений.** Сравнение source с **активной** версией target по версионируемым атрибутам — между значением из источника и колонкой `attribute_current` актуальной строки. Критично: NULL-безопасное сравнение (`IS DISTINCT FROM` в PostgreSQL, hash-diff по конкатенации атрибутов для масштабируемости).

**2. Обработка отсутствия изменений.** Если версионируемые атрибуты не изменились — обновляются только неотслеживаемые атрибуты (SCD1-поля, не участвующие в истории) в текущей строке. Новая строка не создаётся.

**3. Обработка изменения атрибута.** При обнаружении расхождения выполняются три операции, которые должны быть выполнены атомарно в рамках одной транзакции:

* **Закрытие текущей версии (поведение SCD2)**. В актуальной строке сущности фиксируется окончание периода действия: колонка `valid_to` получает дату изменения, флаг `is_current` сбрасывается в FALSE. С этого момента строка перестаёт быть текущей, но сохраняет историческое значение атрибута, действовавшее в её периоде.
	
* **Вставка новой версии (поведение SCD2 + SCD3).** Добавляется новая строка с тем же natural key и новым surrogate key. В историческую колонку записывается новое значение из источника — оно будет отражать состояние атрибута в период действия этой версии. В текущую колонку также записывается новое значение. Устанавливаются `valid_from` = дата изменения, `valid_to` = NULL (high-date), `is_current` = TRUE. Предыдущее значение атрибута остаётся доступным в исторической колонке закрытой строки — это и есть поведение SCD3.
	
* **Распространение текущего значения (поведение SCD1).** Во **всех** исторических строках данной сущности (где `is_current = FALSE`) колонка `attribute_current` перезаписывается новым актуальным значением. Именно этот шаг отличает SCD6 от SCD2: любая историческая строка, к которой обратится запрос за текущим значением, вернёт самое свежее состояние атрибута, без необходимости соединения с актуальной версией или фильтрации по датам. При этом исторические колонки закрытых строк не затрагиваются — хронология сохраняется в неизменном виде.

**4. Новый ключ (No Match).** INSERT новой строки:
`attribute_historical = attribute_current = :value`,
`valid_from = :load_date`, `valid_to = NULL`,
`is_current = TRUE`.

**Защита от ложных срабатываний.** Сравнение на шаге 1 должно корректно обрабатывать NULL-семантику: стандартные операторы при участии NULL возвращают неопределённость и либо не фиксируют переход «пусто → значение», либо дают ложное обновление. Без корректного сравнения повторная загрузка тех же данных будет многократно закрывать и создавать версии, раздувая таблицу.

### Обеспечение целостности и производительности

**Отсутствие пересечений периодов.** В СУБД, поддерживающих диапазонные типы и exclusion-ограничения (например, `DATERANGE` с `EXCLUDE USING GIST`), непересечение интервалов обеспечивается декларативно, что исключает сложную логику проверки на уровне приложения.

**Атомарность.** Операции 3a–3c должны выполняться в одной транзакции. Нарушение атомарности приводит к состояниям, когда либо существуют две «текущие» строки, либо `attribute_current` в истории не соответствует последней версии, либо интервалы дат становятся несогласованными. При конкурентной загрузке — блокировка по natural key либо идемпотентный MERGE.

**Производительность.** SCD6 создаёт больше строк, чем SCD1 или SCD3, и требует UPDATE по всем историческим строкам сущности при каждом изменении — объём таблицы растёт пропорционально частоте изменений, а стоимость записи выше, чем у SCD2. Для смягчения: индексировать natural key и `is_current`; индексировать `valid_from`/`valid_to` для запросов «на дату»; рассмотреть секционирование по `is_current` или диапазону дат при значительных размерах. Запросы к текущему состоянию выполняются по фильтру `is_current = TRUE` и не требуют соединений.
