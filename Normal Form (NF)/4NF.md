### Четвёртая нормальная форма

**Требования:**

- Уже в [[BCNF]]
    
- Нет многозначных зависимостей (когда один атрибут определяет множество значений другого независимо от третьего)

## 4NF — убираем «независимые списки в одной таблице»

### Проблема с точки зрения 4NF

BCNF смотрит только на **функциональные зависимости** (X → Y: «одно значение X даёт одно значение Y»). Но есть ещё **многозначные зависимости** (X ↠ Y: «одно значение X даёт **множество** значений Y, независимо от остальных полей»). Их BCNF не проверяет — а 4NF проверяет.

**Где у нас две независимые «многозначности» про один и тот же объект?**

Посмотрим на заказ. У заказа есть **два независимых списка**:

- список **телефонов** клиента (`Телефоны`);
    
- список **товаров** в заказе (`СоставЗаказа`).
    

Телефоны и товары **друг от друга не зависят**: клиент может иметь 2 телефона и заказать 3 товара, и эти факты независимы.

Пока они лежат в **разных таблицах** — всё хорошо. Проблема появляется, если их **объединить в одну таблицу** «всё про заказ» — что часто хочется сделать «для удобства».

### Демонстрация: объединяем в одну таблицу

`ЗаказДетали` — «всё про заказ в одном месте»

|ЗаказID|Телефон|Товар|
|---|---|---|
|1|111|Хлеб|
|1|111|Молоко|
|1|222|Хлеб|
|1|222|Молоко|
|2|333|Сыр|

**Что случилось:** 2 телефона × 2 товара = **4 строки** для заказа 1, хотя реальных фактов всего 2 + 2 = 4, но не в таком виде: таблица заставляет **перемножать** независимые списки.

Здесь есть две многозначные зависимости:

- `ЗаказID ↠ Телефон` — у заказа **множество** телефонов
    
- `ЗаказID ↠ Товар` — у заказа **множество** товаров
    

И они **независимы** — это и есть нарушение 4NF.


## 4NF — разносим независимые списки обратно

Правило 4NF простыми словами: **если у объекта есть два независимых списка — они должны жить в разных таблицах.**

### `Телефоны` разносится на `ТелефоныЗаказа` и `ОператорыТелефонов`

`ТелефоныЗаказа` (ключ  — `ЗаказID` + `Телефон`)

|ЗаказID|Телефон|
|---|---|
|1|111|
|1|222|
|2|333|

`ОператорыТелефонов` (ключ — `Телефон`)

| Телефон | Оператор |
| ------- | -------- |
| 111     | МТС      |
| 222     | Билайн   |
| 333     | МТС      |

**Изменения:** из `Телефоны` вынесен `Оператор` в отдельную таблицу по ключу `Телефон`. Сама `Телефоны` превратилась в «чистый список телефонов заказа». Связь с оператором теперь через `Телефон`.

### `СоставЗаказа` → `ТоварыЗаказа`

`ТоварыЗаказа` — ключ `(ЗаказID, Товар)`

|ЗаказID|Товар|
|---|---|
|1|Хлеб|
|1|Молоко|
|2|Сыр|

**Изменения**: `СоставЗаказа` переименовывается в `ТоварыЗаказа` для симметрии с `ТелефоныЗаказа`. Структура и данные те же.
