**Conformed Dimension (согласованное измерение)** — измерение, которое используется в нескольких витринах/фактах и означает одно и то же в каждом контексте, где оно используется. Оно имеет **одинаковый смысл**, **одинаковые ключи** и **атрибуты**, и один и тот же **набор значений**.

**Ключевые слова:**

- **Одинаковый смысл** — «клиент» везде означает одно и то же
    
- **Одинаковые ключи** — `client_sk` совпадает между витринами
    
- **Одинаковые атрибуты** — колонки и значения совпадают
    
- **Одинаковая grain — один уровень детализации
    
- **Одинаковые иерархии** — регион → город → магазин везде одинаково

**Что НЕ является conformed dimension:**

- Две разные таблицы `dim_client` с разными ключами
    
- Одинаковое имя, но разный смысл
    
- Одинаковый смысл, но разные атрибуты
    
- Копия измерения, синхронизируемая вручную

**Важно:** conformed dimension — это **не обязательно одна физическая таблица**. Это может быть:

- Одна таблица, используемая всеми витринами
    
- Несколько таблиц с одинаковой структурой и ключами (shrunken, mini)
    
- View поверх общей таблицы
    
- Виртуальное измерение, собираемое на лету

**Главное:** ключи и смысл совпадают.


**Связанные термины:**

- **[[Bus Matrix]]** — карта проекта, где видно, какие измерения общие
    
- **Data steward** — владелец измерения
    
- **Master data** — источник правды для измерения


**Ключевые цели:**

-  Согласованность метрик (один `dim_client` → одно число клиентов везде)
	 
-  Возможность дриллить across витрин (сравнивать и соединять данные из разных витрин)
	 
-  Единая версия правды (одно определение клиента, товара, даты)
	 
-  Переиспользование (одно измерение, 50 витрин используют его)
	 
- Производительность (одинаковые ключи → эффективные JOIN'ы, partition pruning, кэширование)
	
-  Governance (одно измерение → один владелец → один процесс изменения)
	
- Масштабируемость (новую витрину можно собрать быстро, используя готовые conformed dimensions)

### Структура conformed dimension

**Обязательные поля:**

- **Surrogate key** — integer, **генерируется** **централизованно**
    
- **Natural key** — бизнес-ключ из источника
    
- **Attributes** — описательные поля
    
- **SCD-поля** — valid_from, valid_to, is_current (если SCD2)
    
- **[[Unknown member]]** — sk = -1 или 0 для NULL **на источнике**


### Уровни conformed dimensions


- **Identical (идентичные)** — одна и та же таблица используется для всех витрин в неизменном виде
    
- **Shrunken (усечённые)** — подмножество атрибутов, но те же ключи:
```sql
dim_client_full    -- 50 атрибутов (для продаж)
dim_client_shrunk  -- 10 атрибутов (для маркетинга)
client_sk          -- одинаковый
```
    
- **[[Mini-dimension]]** — часто меняющиеся атрибуты вынесены отдельно, но ключи согласованы:
```sql
dim_client                -- (медленные атрибуты)
dim_client_demographics   -- (быстрые атрибуты)
fact_sales                -- ссылается на оба
```
    
- **[[Role-playing]]** — одно измерение в разных ролях, ключи те же:
```sql
dim_date как order_date_sk и ship_date_sk в fact_sales
```
    
- **[[Degenerate]]** — ключ без отдельной таблицы, но согласован:
```sql
order_number в fact_sales и fact_returns
```
    
- **Virtual / View** — view поверх общей таблицы с фильтром или проекцией:
```sql
CREATE VIEW dim_client_active AS
SELECT * FROM dim_client WHERE is_current = true;
```


### Построение conformed dimension

**Шаг 1. Bus Matrix**  
Определить, какие измерения нужны в каких процессах:

| Процесс / Измерение | Дата | Клиент | Товар | Магазин | Сотрудник | Промо |
| ------------------- | ---- | ------ | ----- | ------- | --------- | ----- |
| Продажи             | ✓    | ✓      | ✓     | ✓       | ✓         | ✓     |
| Возвраты            | ✓    | ✓      | ✓     | ✓       |           |       |
| Инвентарь           | ✓    |        | ✓     | ✓       |           |       |
| Маркетинг           | ✓    | ✓      |       |         |           | ✓     |
| Поддержка           | ✓    | ✓      |       |         | ✓         |       |
Столбцы с многими ✓ — кандидаты в conformed dimensions

**Шаг 2. Выбор общих измерений**  
Дата, клиент, товар, гео, сотрудник — почти всегда conformed.

**Шаг 3. Единый источник правды**  
Для каждого измерения — один источник (MDM, справочник, основная система).

**Шаг 4. Согласование атрибутов**  
Какие колонки, какие значения, какие иерархии.

**Шаг 5. SCD-тип**  
Одинаковый для всех витрин.

**Шаг 6. Централизованная генерация ключей**  
Один сервис/процесс генерирует суррогатные ключи.

**Шаг 7. Документация**  
Определение, владелец, правила, каталог.

**Шаг 8. Governance**  
Процесс изменения, согласование, SLA.

### Правила conformed dimension

**Правило 1. Единый суррогатный ключ**  
Один `client_sk` во всех витринах.

**Правило 2. Единый бизнес-ключ**  
Один `client_id` соответствует одному `client_sk`.

**Правило 3. Единые атрибуты**  
Одинаковые колонки и значения.

**Правило 4. Единая гранулярность**  
Один уровень детализации.

**Правило 5. Единые иерархии**  
Регион → город → магазин везде одинаково.

**Правило 6. Единый SCD-тип**  
Везде SCD2 или везде SCD1.

**Правило 7. Единый NULL handling**  
[[Unknown member]] (sk = -1 или 0) для NULL везде.

**Правило 8. Единый timezone**  
UTC везде, локальное — отдельно.

**Правило 9. Единый владелец**  
Data steward для каждого измерения.

**Правило 10. Единый процесс изменения**  
Через governance, не в каждой витрине.
