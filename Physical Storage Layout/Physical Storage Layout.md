**Физический способ хранения (Physical Storage Layout)** — это архитектурное решение уровня СУБД, определяющее, каким образом кортежи (строки) и их атрибуты (столбцы) физически располагаются на носителе (страницах, блоках, файлах).

В профессиональной литературе устоялись термины **row-oriented storage** (строчная ориентация) и **column-oriented storage** (колоночная ориентация), либо сокращённо **row-store** и **column-store**.

### Row-Store (Строчная организация хранения)

**Определение.** В row-store СУБД данные хранятся в виде последовательности кортежей (tuple). На одной **[[Страница (page)|странице (page)]]** размещается несколько строк таблицы, и значения всех столбцов данной строки записываются последовательно друг за другом . Такой подход является традиционным для большинства коммерческих реляционных СУБД (PostgreSQL, MySQL/InnoDB, Oracle по умолчанию).

**Физическая семантика доступа.** При запросе значения конкретного столбца в строке N СУБД вынуждена:

1. Прочитать всю страницу, содержащую строку N, с диска в память;
    
2. Найти в странице саму строку N (со всеми её атрибутами);
    
3. Извлечь значение нужного столбца.


**Следствия для производительности.**

- **Преимущество:** эффективна для операций, требующих доступа ко всей записи целиком (точечные выборки по ключу, `SELECT *`, OLTP-транзакции с частыми `INSERT`/`UPDATE`/`DELETE`). Модификация строки затрагивает одну страницу, что минимизирует накладные расходы на запись.
    
- **Недостаток:** при аналитических запросах, сканирующих лишь несколько столбцов из широкой таблицы, row-store читает с диска избыточные данные (все остальные столбцы), создавая неоправданную нагрузку на I/O[^1].


### Column-Store (Колоночная организация хранения)

**Определение.** В column-store таблица вертикально **[[Партиционирование|партиционируется]]**: значения каждого столбца хранятся непрерывно и отдельно от других столбцов, в собственных страницах или файлах . Каждая страница столбца содержит значения этого атрибута, упорядоченные в соответствии с порядком строк.

**Физическая семантика доступа.** При запросе значения столбца X в строке N СУБД:

1. Читает страницу, где хранится столбец X;
    
2. Находит значение для строки N и возвращает его.

Для запроса, агрегирующего один столбец по всей таблице, column-store читает **только этот столбец**, не затрагивая остальные.

**Следствия для производительности.**

- **Преимущество (I/O):** радикальное сокращение объёма читаемых данных при запросах, затрагивающих подмножество столбцов. Если запрос обращается к 1 из N столбцов, column-store читает примерно 1/N данных по сравнению с row-store.
    
- **Преимущество (сжатие):** непрерывное хранение однотипных значений создаёт высокую степень локальности и повторяемости, что позволяет применять эффективные схемы сжатия (run-length encoding, dictionary encoding, delta encoding) . Сжатие не только уменьшает объём хранения, но и снижает I/O, поскольку с диска читается меньше байт.
    
- **Недостаток (запись):** операции `INSERT`, `UPDATE`, `DELETE` требуют обращения к нескольким страницам (по одной на каждый затронутый столбец), что делает их существенно дороже, чем в row-store . По этой причине column-store ориентированы на read-heavy аналитические сценарии (OLAP), а не на транзакционные (OLTP).


### Гибридные архитектуры хранения (Hybrid Storage Architectures)

**Цель:** сохранить низкую латентность транзакционного доступа и получить высокую пропускную способность аналитического сканирования без ETL-выгрузки.

#### Гибридная таблица: row-partition + column-partition

На уровне одной таблицы данные разделяются на две физические партиции: **row-oriented** (для свежих, часто обновляемых записей) и **column-oriented** (для стабильных, редко изменяемых данных, используемых в агрегациях).

**Механизм:** вставки и обновления направляются в row-партицию; фоновый процесс асинхронно перемещает «остывшие» записи в column-партицию. Поиск по первичному ключу сначала выполняется в row-партиции; column-партиция подключается только при необходимости (например, для агрегатных запросов) . Для ускорения фильтрации применяются Min-Max индексы[^2] , позволяющие пропускать column-партиции, заведомо не содержащие искомых значений.

**Компромисс:** row-партиция не сжимается, поэтому её размер искусственно ограничивается для экономии памяти; column-партиция обеспечивает сжатие и быстрый OLAP.

#### Некластеризованный columnstore-индекс на rowstore-таблице

Реализация в SQL Server (с 2016): таблица физически остаётся row-store, но для выбранных столбцов создаётся **обновляемая колоночная копия** (некластеризованный columnstore-индекс). Транзакции продолжают работать через rowstore, аналитические запросы — через columnstore-индекс; синхронизация происходит при каждом изменении данных.

**Компромисс:** columnstore-индекс требует дополнительного дискового пространства (хотя сжатие в среднем ~10×), но не требует изменения логической модели данных и не блокирует OLTP.


#### HTAP-архитектуры: классификация по расположению row и column

**Выделяют четыре архитектурных паттерна HTAP-систем:**

- **Primary Row Store + In-Memory Column Store:** первичное хранилище — row-store (источник истины для транзакций); в памяти поддерживается колоночная реплика для аналитики.
  **Пример:** SQL Server с memory-optimized columnstore.
	
- **Distributed Row Store + Column Store Replica:** row-store распределён, колоночная реплика поддерживается на отдельных узлах.
  **Примеры:** TiDB, PolarDB.
	
* **Primary Row Store + Distributed In-Memory Column Store:** Комбинация распределённого row-store с распределённым in-memory column-store.
  **Пример:** SAP HANA (с оговоркой, что HANA по умолчанию column-oriented, но поддерживает row-таблицы для точечных нагрузок).
	
* **Primary Column Store + Delta Row Store:** Первичное хранилище — column-store; row-store используется как **delta-буфер** для свежих вставок и обновлений. Периодически delta сливается (merge) в columnstore.
  **Примеры:** ClickHouse (с движком для быстрых вставок), Vertica.



[^1]: **Input/Output** — операции чтения и записи данных между оперативной памятью и постоянным хранилищем.

[^2]: **Min-Max индекс** — это обобщённое название класса структур доступа (также известных как zonemap или block range index), которые хранят минимальное и максимальное значения столбца для группы физически смежных строк
