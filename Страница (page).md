**Страница (page)** — это **наименьшая единица физического хранения** в СУБД, используемая для чтения и записи данных на устройство хранения.

Страница представляет собой блок данных фиксированного размера, который СУБД считывает с диска в память или записывает из памяти на диск за одну операцию ввода-вывода.
То есть движок базы данных читает или записывает всю страницу с диска, а не отдельные строки.

Размер страницы фиксирован для конкретной СУБД (и фиксируется при инициализации БД), и внутренняя структура страницы определяет, как строки физически размещаются на ней и как они адресуются.


## Общая структура страницы

```text
┌─────────────────────────────────────────────┐  ← начало страницы (offset 0)
│  Заголовок страницы (Page Header)            │
│  - идентификатор/номер страницы              │
│  - тип страницы                              │
│  - уровень в B-дереве (для индексных)        │
│  - ссылки на соседние страницы (prev/next)   │
│  - LSN (log sequence number)                 │
│  - объём свободного места                    │
│  - счётчик записей                           │
│  - флаги состояния                           │
│  - контрольная сумма (checksum)              │
├─────────────────────────────────────────────┤
│                                             │
│           Область данных (слоты)            │
│           записи/строки/кортежи             │
│                                             │
│                    ↓                        │
│              (растёт вниз)                  │
│                                             │
│ ~~~~~~~~~~~~ свободное пространство ~~~~~~~~│
│                                             │
│              (растёт вверх)                 │
│                    ↑                        │
│                                             │
│        Массив слотов / слот-директория      │
│        (slot array / line pointer array)    │
│        - для каждой записи: смещение,       │
│          длина, флаги                       │
├─────────────────────────────────────────────┤
│  Служебный трейлер (если есть)              │
└─────────────────────────────────────────────┘  ← конец страницы
```


### Заголовок страницы (Page Header)

Служебная область фиксированного размера. Типичное содержимое:

- **Идентификация**: номер страницы (page ID), идентификатор файла/табличного пространства. Часто page ID = (file_id, page_number) — это и есть физический адрес.
    
- **Тип страницы**: данные, индекс, карта свободного пространства, overflow, системная, метаданные и т.д.
    
- **Служебные ссылки**: для индексных страниц — указатели на левую/правую соседнюю страницу того же уровня (облегчает сканирование диапазонов); для страниц данных — иногда ссылки на связанные overflow-страницы.
    
- **LSN (Log Sequence Number)**: номер последней операции в журнале транзакций, повлиявшей на эту страницу. Критично для WAL-восстановления и для проверки «не устарела ли» страница в буферном пуле.
    
- **Счётчик записей** (число активных слотов).
    
- **Объём свободного места** — чтобы не пересчитывать каждый раз.
    
- **Уровень в B-дереве** (для индексных страниц): 0 — лист, >0 — внутренний узел.
    
- **Флаги состояния**: «грязная», «закреплена», «под repair» и т.п. (часто часть флагов живёт в буферном пуле, а не на диске).
    
- **Контрольная сумма**[^1] страницы — для обнаружения повреждений при чтении с диска.


### Слот-директория (Slot Array / Line Pointer Array)

Это массив **небольших фиксированных элементов**, по одному на каждую запись на странице. Каждый слот (line pointer) содержит:

- **offset** — смещение начала записи внутри страницы;
    
- **length** — длина записи;
    
- **flags** — например, «запись удалена» (tombstone), «запись перенесена», «запись — это redirect на другую страницу».
    

Зачем нужен слот-массив, а не просто подряд идущие записи:

1. **Косвенная адресация.** Внешние ссылки (из индексов, из других страниц) указывают не на физический offset, а на **номер слота** (slot number / line pointer). Запись можно физически переместить внутри страницы (при дефрагментации, при обновлении), поменяв только offset в слоте — внешние ссылки остаются валидными.
    
2. **Удаление без сдвига.** Удаление записи = пометить слот как «мёртвый» (или освободить). Физическое место освобождается позже при уплотнении. Это дёшево.
    
3. **Быстрый доступ.** Найти i-ю запись — это O(1) по слоту, а не сканирование.
    
4. **Учёт свободного места.** Число слотов и их состояние дают картину занятости.

Слоты обычно нумеруются с 0 или 1 и **никогда не переиспользуются** для других записей в пределах «жизни» страницы без специальной процедуры уплотнения — чтобы не сломать существующие ссылки.


### Область данных и размещение записей

Записи (кортежи, index entries[^2]) укладываются в область данных. Особенности:

- **Переменная длина.** Запись может быть фиксированной или переменной длины; переменная длина — обычное дело (например, VARCHAR).
    
- **Выравнивание.** Записи часто выравниваются по границе слова/8 байт для производительности CPU.
    
- **Внутренняя структура записи** (типично):
    
    - заголовок записи: длина, флаги, число колонок;
        
    - NULL-битмапа (какие поля NULL);
        
    - значения полей (fixed-length впереди, variable-length — со смещениями);
        
    - для MVCC-СУБД — версионные поля (ID транзакции создания/удаления).
        
- **Порядок записей** на странице данных, как правило, **не гарантирован** и не совпадает с логическим порядком (он определяется индексами). На индексных листовых страницах записи, наоборот, упорядочены по ключу.


### Свободное пространство и его учёт

Между слот-массивом и данными — свободная зона. СУБД должна уметь ответить: «поместится ли сюда новая запись длиной N?». Учёт ведётся:

- **в заголовке** (агрегированный объём свободного места, иногда с разделением «непрерывный кусок» vs «суммарно с учётом дыр»);
    
- **во внешних картах** (free space map / PFS / bitmap-страницы) — чтобы при вставке не читать каждую страницу, а знать, где есть место.

**Различают:**

- **непрерывное свободное место** — можно вставить запись, не перемещая ничего;
    
- **суммарное свободное место с учётом «мёртвых» слотов и дыр** — требует уплотнения (compaction / defragmentation), чтобы собрать дыры в один кусок.


## Операции и их взаимодействие со структурой

**Вставка (INSERT):**

1. Проверить, хватает ли свободного места (по заголовку/карте).
    
2. Взять следующий свободный слот (или добавить новый в слот-массив).
    
3. Записать данные в свободную область, сдвинув границу данных.
    
4. Обновить offset/length в слоте, счётчики и LSN в заголовке.

**Удаление (DELETE):**

1. Пометить слот как «мёртвый» (или обнулить) — данные физически остаются.
    
2. Обновить счётчики, LSN. Место вернётся в оборот только при уплотнении/вакууме.

**Обновление (UPDATE):**

- _Same-page, влезает на место_ — перезапись in-place (с обновлением length, если длина изменилась).
    
- _Влезает, но не на то же место_ — новая версия пишется в свободную область, слот перенаправляется (offset меняется), старая версия становится «мёртвой». Внешние ссылки по номеру слота остаются валидными.
    
- _Не влезает_ — запись переносится на другую страницу, в слоте остаётся **redirect**-указатель. Это называется «forwarded record» / «tuple moved».[^3]
    
- В MVCC-СУБД обновление обычно = новая версия записи + пометка старой; физическая чистка — отдельно (vacuum).

**Уплотнение (compaction / defragmentation):**

- Сдвиг живых записей к началу области данных, сборка дыр в один непрерывный кусок.
    
- Обновление offset'ов в слотах. Внешние ссылки (по номеру слота) при этом **не меняются** — в этом и смысл слот-директории.
    
- Обычно делается лениво: при вставке, при vacuum, при реорганизации.


## Целостность и восстановление

- **Контрольная сумма** страницы проверяется при чтении; при несовпадении — ошибка/попытка восстановления из реплики или бэкапа.
    
- **LSN**[^4] в заголовке сравнивается с LSN в журнале: так реализуется WAL-восстановление (повтор операций после сбоя) и правило «не записывать на диск страницу, чей LSN меньше уже сброшенного в журнал» (write-ahead logging).
    
- При сбое посередине записи страницы на диск возможна **torn page** (частичная запись). Защита — контрольные суммы, двойная запись (doublewrite buffer[^5]), полные страницы в журнале (full page writes) — механизмы различаются, но цель одна: не дать полузаписанной странице попасть в файл данных.


## Варианты и отклонения от модели

Хотя модель «заголовок + слоты + данные» доминирует, есть вариации:

- **Страницы без слот-массива**: например, некоторые append-only/columnar-форматы хранят данные плотным блоком с отдельными метаданными (min/max, зоны) — там нет нужды в косвенной адресации построчно.
    
- **Columnar-страницы**: хранят значения одного столбца (или группы) для многих строк; структура — заголовок + сжатые блоки значений + зоны/словари, без построчных слотов.
    
- **Overflow-страницы**: продолжение большой записи, которая не влезла в основную; связаны цепочкой или прямыми ссылками.
    
- **Страницы с «tombstone»-маркерами**[^6] вместо физического удаления (LSM-подобные и MVCC-системы).
    
- **Разные размеры**: 8 КБ, 16 КБ, 32 КБ и т.д.; размер фиксирован для данного табличного пространства.


[^1]: **Контрольная сумма** — это компактное числовое значение, вычисляемое из содержимого объекта по определённому алгоритму.
<br>
[^2]: **Index entry** — это элемент индексной структуры, который связывает ключ с местоположением строки в таблице
<br>
[^3]: или применяется другой механизм, позволяющего обходить ограничение фиксированного размера страницы и хранить значения полей, превышающие этот размер.
<br>
[^4]: **LSN (Log Sequence Number, номер последовательности журнала)** — это монотонно возрастающий уникальный идентификатор, присваиваемый каждой записи в журнале транзакций.
<br>
[^5]: Перед записью страницы в файл данных СУБД пишет её **сначала в отдельную область на диске — doublewrite buffer**, и только потом — в основное табличное пространство.
<br>
[^6]: **Tombstone (надгробие)** — это маркер «удалено», который физически не стирает данные, а помечает их как логически удалённые.
	В MVCC старые снапшоты транзакций должны продолжать видеть строку, поэтому физически удалять нельзя, пока её видят активные транзакции. **Tombstone** помечает «удалено для новых», а старые версии живут до очистки.
